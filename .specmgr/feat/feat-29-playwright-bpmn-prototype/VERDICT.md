# feat-29 prototype — verdict

Question (per the plan's Overview and REQ-007): **is Playwright + Modeler
a viable foundation for agent-driven BPMN editing?** — the user proposal
(2026-11-18) under test: a local page hosting the full bpmn-js Modeler,
driven by the agent through the Playwright MCP (load, save, draw),
delivering agent-driven BPMN editing without the file-backed MCP
server's tool layer. This file adds no new measurements: it derives the
verdict from the six rubric rows R1–R6 in `results.md`, each of which
references the raw data under `bin/logs/`.

Date: 2026-11-21 (the finalization of the run; Phases 140–190 hold the
evidence, Phase 200 finalizes and verdicts).

## Verdict

**conditional.** The stack delivered what its runs claimed: 10/10
first-try primitives (R1), 3/3 pixel and 3/3 bridge full draws with
0/0/0 structural deviation (R2/R4), model-faithful and idempotent saves
(R5), and a working human-in-the-loop leg (R6) — so Playwright + Modeler
can carry agent-driven BPMN editing. But the proposal's headline claim —
"without the file-backed MCP server's tool layer" — does not survive the
evidence: `browser_snapshot` exposes no BPMN model fact at all, so the
agent is blind without an in-page state channel (the bridge) that every
run, pixel or bridge, used to verify its results (R3), and the page's
saves are not byte-equivalents of the server's serialization and carry a
fresh, disjoint factory id set on every draw (R5, R2/R4). The foundation
is viable under three conditions: the in-page bridge is a first-class
part of the page (the agent's eyes), the pixel protocol carries its
established preconditions (loaded baseline, click-create, Escape after
create, DOM aiming, palette re-arm), and id/serialization authority stays
with the file-backed server (the page's output is normalized on ingest).

## Predicted cons vs. held pros

The proposal's expected profile (the plan's Overview; DEC
fdc84432-1b48-4eb9-82e0-ec13cb8cf8ba, Option 1 and its Stage 2 note):
three predicted pros (P1–P3) and five predicted cons (C1–C5), each
checked against the run's data.

Predicted pros:

- **P1 — no tool layer needed (the agent drives a real Modeler): did not hold.** R3: `browser_snapshot` exposes no model fact; every verification in the run went through the in-page `__bpmn` bridge (or a DOM `browser_evaluate` probe) — the bridge IS a tool layer, and without it the pixel strategy "has hands but no eyes" (R3 verdict; `140-120-r3-raw.md`).
- **P2 — full Modeler fidelity (everything a human can do, the agent can do): held, with two visible edges.** The agent drove the full Modeler — palette create, global connect, inline rename, load, save, element drag (R1 10/10; R2 3/3 full draws; R6 the human used the same page for a drag). Edges: the headless HTML5-DnD palette drag never completes in this browser build (`130-120-smoke.md` finding 1 — the click-create session is the pixel path), and the palette icons were missing for everyone until the human leg reported it (R6 — a page bug, not a Modeler limit).
- **P3 — human-in-the-loop for free (the same page is a normal editor): held.** R6: the user leg (load, inspect, four renames, one move, save) worked with zero protocol support, and the same page's first human-eyes review found the one bug every automated gate missed (`190-120-r6-raw.md`, `190-120-iconfix.md`).

Predicted cons:

- **C1 — the agent is blind without a state channel (pixels expose no model facts): materialized exactly as predicted.** R3 verdict: no ids, types, coordinates, zoom, connectivity, or selection binding in the snapshot; the implication paragraph states the pixel strategy cannot stand alone, and every R1/R2 row records which state channel confirmed the result.
- **C2 — UI automation flakiness (headless DnD limits, auto-opened editors, aiming): mostly avoided, with the predicted surfaces as its visible edges.** 0/0/0 deviation and 0 retries across 3/3 pixel full draws (R2) — but the run only got there via the workarounds the con named: the click-create session instead of the DnD drag (the headless limit), the Escape after every creation (the auto-opened label editor), the DOM `data-element-id` aim probe (aiming), and the palette re-arm before each connect (the one-shot tool). The flakiness did not fire; its surface area IS the precondition list.
- **C3 — serialization/id stability vs the file-backed server: materialized.** R5: the page's saves are compact (`format: false`, no EOF newline) against the server's `format: true`, and carry one extra empty `BPMNLabel` after a rename — model-faithful but not byte-equivalent; R2/R4: six mutually disjoint factory id sets for the same pinned model (72 unique ids, 0 shared), plus the 12/12 pinned-id gap (no id surface on the page — R3 — and no id parameter in the bridge API).
- **C4 — an extra always-on local server + fixed port: materialized.** The entire run lived on 127.0.0.1:8123 (the fixed port, chosen against the system-owned 8080): page, assets, bridge, and file API all needed it up, every evaluation phase began by confirming it, and the close leaves it stopped with the port free (`bin/logs/server.pid`, the per-phase start/verify scripts).
- **C5 — a real-time two-way canvas would still need a separate canvas-server process (DEC fdc84432, Option 1 "Bad"; the `yctimlin/mcp_excalidraw` precedent): not testable here.** This run is the turn-based Stage 1 shape (an explicit preview step reloads the current diagram); no two-way synchronization was attempted, so the con stands as the DEC's prediction. What R6 does add: even the turn-based same-page human/agent flow depended on the bridge + file API as its shared state — the state channel the DEC's canvas-server shape would have to carry (see the recommendation).

## Project-direction recommendation (feeding the Stage 2 decision per DEC fdc84432, still draft)

This run feeds, and does not change, DEC fdc84432. The evidence says:

1. **Keep the file-backed MCP server as the id/serialization-authoritative layer.** R5 shows the page's saves are model-faithful and idempotent but not byte-equivalents of the server's files (formatting, the `BPMNLabel` side effect), and R2/R4 show a fresh factory id set on every draw (six disjoint sets for one model; the 12/12 pinned-id gap). Anything that byte-diffs, version-stamps, or addresses elements by id across sessions must normalize through the server's `serializeBpmn` / `collectAddressableInventory` path — the page is an editing front-end that round-trips files through the server, not a second source of truth. If pinned ids become a requirement, that is an API addition on the server side (the user's considered Option C), not a page-side fix: neither strategy could set ids here.
2. **Keep a Playwright-driven Modeler page as a local edit/preview channel — with the bridge first-class.** R3 makes the in-page state channel a hard precondition (the agent is blind without it), so the page's contract is Modeler + bridge + file API, not "just a page". R4's head-to-head (15 vs 29–43 calls per draw; zero aiming/editor/DnD/re-arm surface) says the agent's editing workload should ride the bridge as the primary channel; pixels remain valuable as (a) the proof the page is a real editor (R1/R2) and (b) the human channel (R6). Conditions for keeping it: the established pixel preconditions become documented protocol (loaded baseline, click-create, Escape after create, DOM aiming, palette re-arm), saves go through the server's serialization (point 1), and the unmodified bpmn.io watermark stays (verified in every snapshot — R3).
3. **A Stage 2 live canvas must carry over three things from this run:** the in-page bridge (the state channel — R3/R6 show both the agent and the human leg depend on it), the turn-based file API as the persistence contract (bytes stay server-authoritative — R5), and the watermark clause (DEC fdc84432 consequence). Its shape stays the DEC's Option 1 "Bad" / More Information prediction — a separate canvas-server process (web UI + REST + WebSocket sync, the `yctimlin/mcp_excalidraw` model) next to the MCP server process; nothing in this run contradicts that, and nothing in it can validate it (C5: not testable here).

## Caveats (the run's known constants)

- **Headless-only, one browser build:** HeadlessChrome 157.0.0.0 (user constraint; `130-110-browser-version.log`). Headed Playwright is out of scope for this run; the DnD limitation (the C2/P2 edge) is measured in this headless build and may behave differently elsewhere.
- **Session latency in the R2/R4 wall times:** the per-MCP-call round-trip latency decayed across the session (R2 ≈ 109.5/82.3/50.9 s per call, R4 ≈ 50.8/41.6/44.4 s), so the raw wall-time gap is dominated by call count plus latency; per-call, the two strategies are the same order.
- **The R2 structural metric is the user-approved Option A** (D1 shape counts + D2 flow count + D3 connectivity/types) with the **12/12 id gap recorded as a constant**: the pinned ids (`start`/`task`/`gw`/`task1`/`task2`/`end`, `f1`–`f6`) are unmatchable against the factory-generated actual ids under either strategy (no id surface on the page — R3 — and no id parameter in the bridge API), so the structural score is the deviation meter.
- **The commit-time +1 EOF byte:** the pre-commit hook adds a trailing newline to `files/` artifacts at commit time (the R5 byte policy); every comparison in the run was on the uncommitted on-disk bytes.
- **The human leg ran over an SSH port-forward** to 127.0.0.1:8123 because sys0's local display was not up — the same fixed endpoint the plan's connect steps name (an environment note, not a protocol deviation).
